# 技術簡報

命題六：物流與宅配服務 — AI 智慧配送路線與載重規劃 Agent
<https://ai-dispatch-control-tower.onrender.com/>

---

## 1. 一句話

**調度員用講的指揮，AI 只負責聽懂；所有數字由確定性程式算，所有變更由人確認。**

不是「AI 幫你排班」，是「AI 讓你能用講的去改一個確定性的排班系統，而且每一個選項都附代價」。

## 3. 架構

```
 瀏覽器（React 控制塔）
   │  一個 origin,前端 bundle 與 API 由同一個容器供應
   ▼
 FastAPI
   ├── 語意層（唯一會呼叫模型的地方）
   │     ├─ 主 Agent：28 個 function tool,strict schema
   │     ├─ 急單理解 Agent：結構化抽取,不執行任何動作
   │     ├─ 欄位補填 Agent：把講的值對到留白的儲存格
   │     ├─ 欄位對映 Agent：只對映「欄位名稱」,永不讀寫儲存格的值
   │     └─ Input guardrail：語意判斷 prompt injection
   │
   └── 確定性層（模型碰不到）
         ├─ importer     讀 xlsx、驗必填、彙總包裹重量
         ├─ matrix       距離／時間矩陣（SIMULATED，Google Routes 停用）
         ├─ planner      OR-Tools：載重上限、責任區、配送時段、站序
         ├─ validator    獨立重算一次,不信 planner 自己報的數字
         ├─ plan_diff    兩個版本差在哪、代價多少
         └─ repository   SQLite：不可變版本 + 稽核紀錄
```

| 為什麼分成兩層 | |
|---|---|
| 語意層 | 只回答「使用者想做哪一件事、講了哪些欄位」。輸出是結構化物件,不是句子,也不是數字 |
| 確定性層 | 所有重量、距離、時間、可行性、版本狀態。同樣輸入永遠同樣輸出 |
| 介面 | 工具的 docstring 決定路由；回覆的文字在工具選完之後才產生 |

## 5. 三個階段＝同一個求解器，三組不同的鎖

| 階段 | 畫面 | 鎖住什麼 | 還能動什麼 |
|---|---|---|---|
| 上車前 `PRE_LOAD` | 貨還在站內 | 無 | 全部：車輛指派、站序 |
| 上車後 `LOADED` | 貨已上車 | **既有訂單不能換車** | 站序、插新的急單 |
| 已發車 `DISPATCHED` | 車在路上 | 已送站點 + 車輛指派 | 只有還沒送的站的順序 |

這是整個系統最值得講的一件事：**不是三套演算法，是同一個模型隨時間增加約束**。既成事實越多，可變動的決策變數越少。

時窗定義：基準 09:00；早上 0–3h、下午 4–8h、晚上 8–11h；每站服務 180 秒。

## 6. AI 做什麼、不做什麼

| AI 做 | AI 不做 |
|---|---|
| 判斷這句話是哪一種操作 | 加總重量 |
| 從自然語言抽出欄位（訂單編號、座標、時段…） | 判斷合不合法 |
| 把「早上送」對到 `MORNING` | 指派車輛 |
| 把「20 公斤以內」對到規則的參數 | 排站序 |
| 判斷是不是 prompt injection | 檢查時段 |
| 對映 Excel 的欄位**名稱** | 填任何儲存格的**值** |
| | 轉換方案狀態 |

**畫面上每一個數字都來自後端確定性計算。** 這句話寫在畫面最下面，是可以被檢查的。

## 7. 安全邊界

| 項目 | 做法 |
|---|---|
| Agent 架構 | 單一 Agent。不使用 handoff、multi-agent、A2A、AP2 |
| Prompt injection | Input guardrail 以語意判斷（結構化輸出），不是關鍵字比對。急單與補欄位的抽取 Agent 也掛同一個 guardrail |
| 資料當指令 | Excel 的 `note` 欄寫指令不會被執行（有專門的測試 `R5-guardrail-note`） |
| 方案生效 | Preview 版本不可變、不覆寫；**人工確認是唯一生效途徑**，每次確認寫稽核紀錄 |
| 驗證 | 每個方案都過獨立 Validator（重新算載重、責任區、重複、時窗）；沒過不准確認 |
| 外部副作用 | `DISPATCH_ENABLED` 預設 `false`，不會真的派車 |
| 金鑰 | Server key 永不進 browser bundle；`.env` 不提交 |
| 個資 | 不使用真實姓名、電話、完整地址 |
| 地圖 | Google Routes／Maps 停用，全程 `SIMULATED` + OSM 底圖，畫面標示「模擬資料」 |

## 8. 數字

**OR-Tools 對照 baseline（同一份矩陣，公平比較）**

| 資料 | 方法 | 里程 | 行駛 | 載重落差 | 排不進去 | 求解 |
|---|---|---|---|---|---|---|
| demo-50-tight | baseline | 156.9 km | 327 分 | **0.995** | **4 張** | 1 ms |
| | OR-Tools | 164.7 km | 343 分 | **0.352** | **1 張** | 43 ms |
| demo-50-relaxed | baseline | 139.0 km | 289 分 | **1.000** | **5 張** | 1 ms |
| | OR-Tools | 165.9 km | 346 分 | **0.129** | **0 張** | 37 ms |

**里程反而多了 5～19%，這是誠實的數字，也是重點**：baseline 之所以「短」，是因為它把 4～5 張單直接丟掉不送，而且把貨全堆在一台車上（載重落差 1.000 ＝ 一台滿載、一台空車）。要把單全部送完、而且讓四個司機工作量平均，就是得多跑。

要最短里程可以切 `FASTEST` 目標（164.7 km）；demo 用的是 `BALANCED`。三個目標的取捨畫面上寫得出來。

## 9. 評審會問什麼

| 問題 | 怎麼答 | 現場怎麼證明 |
|---|---|---|
| 這些數字是 AI 算的嗎？ | 不是。模型不產生任何數字，只做語意。重量、距離、時段、可行性全部是程式 | 畫面最下面就寫著「所有數字來自後端確定性計算」。同一份檔案重排結果完全一樣 |
| 缺欄位那段是不是寫死的？ | 不是，是讀檔案的必填欄位檢查 | **現場挖掉任何一格**再丟上去，它會報那一格。我挖過 ORD-037 地點、ORD-012 時段、PKG-025-01 重量，報的都是對的 |
| 你怎麼確定它沒有亂編？ | 沒講的欄位它會反問；依區域補的值會**明講是它補的** | 第五幕：只給座標和區碼，畫面寫「臺北市大安 是我依 Z3 區補的，不對就跟我說」 |
| 為什麼有一張排不進去？ | ORD-050 是 170 公斤，最大的車上限 160 公斤，**空車也裝不下** | 看板最下面直接寫這句話，不是印代碼 |
| 做不到的時候會怎樣？ | 直說做不到，而且把按鈕鎖起來 | 第六幕：要求中午前送到，回「最快只能到 13:38，晚 1 小時 39 分鐘」，方案卡標「需人工處理」，【確認套用】按不下去 |
| 用了幾個 Agent？ | 主流程單一 Agent，28 個工具。另有三個只做結構化抽取、不執行動作的小 Agent（急單理解、欄位補填、欄位對映）與一個 injection guardrail | 架構圖 |
| 為什麼不用 multi-agent？ | 調度是有狀態、要可稽核的流程。多 Agent 之間的交接是新的失敗面，而這個題目的難點在「約束正確」不在「分工」 | — |
| 怎麼防 prompt injection？ | Input guardrail 用語意判斷，不是黑名單；Excel 的資料欄寫指令也不會被執行 | 有專門測試 `R5-guardrail-note` |
| 排班品質比得上人工嗎？ | 對照 baseline：未安排從 4～5 張降到 0～1 張，載重落差從 1.000 降到 0.13～0.35 | 上面的 benchmark 表 |
| 里程怎麼反而變多？ | 因為 baseline 少送 5 張、還把貨全堆在一台車。全部送完＋工作量平均就是會多跑。要最短可以切 FASTEST | 三個目標的對照 |
| 上車後還能插單嗎？ | 可以。貨已經在車上，所以**既有訂單一張都不能換車**，只能插新的、調剩下的站序 | 第五幕 ORD-104 → 第二車第 3 站，換車 0 張 |
| 發車後呢？ | 只能重排還沒送的站。已送的鎖死，拖也拖不動 | 第六幕時間軸，已完成站點不能拖曳 |
| 會不會自己偷偷改方案？ | 不會。Preview 不可變，人按確認才建立新版本，每次都寫稽核 | 方案卡上寫「這只是預覽，還沒套用」；確認後才變「已建立新版本」 |
| 可以還原嗎？ | 可以，版本是不可變的，有上一步／下一步 | 看板上方的【上一步】【下一步】 |
| 為什麼下午才發車？ | 沒有。早上有發車（第三車 09:24、第四車 09:25），21 張早上的單全在早上送完。看板第一欄顯示 13:00 是因為那台車身上全是下午晚上的單 | 切「早上」篩選看時間 |
| 換一份格式不同的 Excel 會怎樣？ | 會先做欄位對映，且**只對映欄位名稱**，不會讀值去猜；信心不足就要人確認 | 有測試 `F1-02～F1-07` |
| 資料會留下來嗎？ | Render 上 SQLite 放 `/tmp`，重啟就清掉。這是示範環境的刻意選擇 | — |
| Google Maps 呢？ | 開發期間一律停用，用模擬矩陣＋OSM 底圖，畫面標示「模擬資料」。介面已經接好，換金鑰就能切 | 畫面右上角那行字 |

## 10. 誠實的限制

| 限制 | 說明 |
|---|---|
| 路況是模擬的 | 距離／時間來自固定矩陣，不是即時路況。介面已抽象化，接回 Google Routes 只是換 provider |
| 資料不落地 | Render free plan，SQLite 在 `/tmp`，服務重啟就沒了 |
| 冷啟動 40 秒 | free plan 會休眠，上台前先打一次網址暖機 |
| 補欄位的暫存 | 被擋下來的檔案放在記憶體（上限 8 份）。丟完檔案隔太久才補值，token 會過期，重傳一次即可 |
| 點名車輛偶發 | 「三號車的老王…」這種句子單獨測 12/12 正確，但對話跑很多輪之後約 1/20 會退成「請先選擇要限制的車輛」。再講一次車號即可 |
| 不做正式派車 | `DISPATCH_ENABLED=false`，不對外送出任何指令 |
