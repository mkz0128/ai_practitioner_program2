## 【B】對話訊息精簡（4 件）

### B-1　規則試算列出 19 張訂單編號

`src/agent/runtime.py:976`：

```python
+ f"。影響訂單：{affected_text}；試算後最後一站預估 {last_eta_text}。"
```

實際跑出來是這樣（沒人會看）：

```
影響訂單：ORD-013、ORD-014、ORD-015、ORD-017、ORD-025、ORD-026、ORD-027、
ORD-028、ORD-029、ORD-030、ORD-031、ORD-032、ORD-033、ORD-044、ORD-045、
ORD-046、ORD-047、ORD-048、ORD-049；試算後最後一站預估 18:03。
```

**改法**：**超過 3 張就不要列編號**，改成講數量與影響：

```
VEH-002｜今天｜單件 ≤ 20 kg｜最後送達 ≤ 17:00
  19 張改派、1 張排不進去
  最後一站 18:25 → 16:48
  49/50 不變
```

編號明細移到卡片的展開區（要看才點開）。

### B-2　套用規則後要說明載重為什麼變不平均 ← **重要**

使用者實測：套用「VEH-002 單件 ≤ 20 kg ＋ 五點前收工」之後，
**VEH-002 掉到 18%、VEH-001 衝到 93%**，看起來像排錯。

**那是規則正確生效的結果，但系統沒說。**

**改法**：套用後要主動講一句：

```
因為這條規則，VEH-002 少了 19 張（82% → 18%），
這些單主要由 VEH-001 接手（57% → 93%）。
如果要讓載重平均一點，可以放寬重量上限或收工時間。
```

數字一律由確定性程式算。

### B-3　急單缺欄訊息太複雜

`src/api/main.py:3215-3216`：

```
目前還不能計算。第 1 張急單 缺少：訂單編號、地點名稱、城市、行政區、
座標、配送區域、每件重量、包裹件數、配送時段。請一次補齊後再繼續。
```

兩個問題：

1. **「第 1 張」誤導** —— 使用者說「三張急單」但沒給資料，系統只建了一張草稿，
   訊息卻寫「第 1 張」，看起來像它只處理第一張。
   **只有一張草稿時不要寫「第 N 張」。**
2. **九個欄位名太長**，改成白話分組：

```
還需要這些才能算：
  訂單編號、座標、配送區域
  重量、件數、配送時段
```

### B-4　成效回顧沒有意義

`src/services/dispatch_deviations.py:143-167`、`src/agent/runtime.py:1397`。

實測輸出：

```
今天回顧：VEH-003 今天實際比預估慢 4 分鐘。已記錄。
VEH-002 今天實際比預估慢 3 分鐘。已記錄。
VEH-004 今天實際比預估慢 1 分鐘。已記錄。
Z3 區每站停留時間平均比預估多 6 分鐘。已記錄。
建議將 Z3 的服務時間由 3 分鐘調整為 9 分鐘。
```

**慢 1 分鐘、3 分鐘沒有人在乎，「已記錄」也是廢話。**

**改法**：改成講「**明天會怎樣**」，而且先給總覽：

```
今天 52 張全部送達，總里程 231 公里，平均載重 58%。

一、Z3 區每站多花 6 分鐘。如果明天 Z3 還是 12 張，會多花 72 分鐘，
    最後三站會掉出配送時段。
二、VEH-002 因為今天的重量限制少跑 19 張，VEH-001 載重衝到 93%。
    明天如果限制還在，建議把重單分一部分給 VEH-003。

要我把這些寫進明天的排班參數嗎？
```

規則：
- **先講總覽**（幾張、幾公里、平均載重）
- **只列會影響明天的**，慢 5 分鐘以下不要單獨列
- **每一點都要講後果**，不要只講現象
- **拿掉「已記錄」**
- 這一則**不出卡片**，追問「那明天要怎麼改」才出 `[套用建議] [先不要]`
