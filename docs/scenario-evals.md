# 情境 Evals

## 這份文件跟 `acceptance-tests.md` 的差別

`acceptance-tests.md` 驗「功能在不在」。這份驗「**答案對不對**」。

先前的驗收之所以會讓錯誤概念連過四輪，是因為測項只寫「卡片要有代價數字」，沒寫「代價必須合理」。因此本檔的每一條都必須同時定義：

| 欄位 | 意義 |
|---|---|
| **輸入** | 使用者實際會打的字，逐字照打，不得改寫成系統聽得懂的版本 |
| **正確** | 通過的條件 |
| **判定失敗** | 明確列出什麼結果算錯。**只要命中任何一條就是 FAIL** |

**規則：不得為了讓測試通過而修改「輸入」欄位的句子。** 使用者不會照系統的規格講話。如果系統聽不懂，那是系統要修，不是句子要改。

執行方式：Codex 自己開瀏覽器、用鍵盤實際打字、1440×900、全程監看 Console 與 Network。

### A 區塊的補齊規則

**補齊訊息只能包含系統點名的欄位，不得多給。**

## K 意圖路由（跨資料、跨說法）

**這一區塊是為了證明系統是在理解語意，不是在比對測試檔裡出現過的句子。**

硬性規定，違反其一即整區塊不通過：

1. **每一句都要在三組資料各跑 2 次**：`demo-50-relaxed.xlsx`、`demo-50-tight.xlsx`、
   `demo-delivery-40-orders.xlsx`。只在一組資料上通過不算通過。
2. **不得把測項的句子加進任何 prompt、few-shot 或分類器提示詞**。修好的方式必須是
   讓分類邊界正確，不是讓系統認得這幾句。
3. **不得為了讓測試通過而修改「輸入」欄的句子。**
4. 判定依據是 `evidence[-1]["tool"]`，不是回覆文字讀起來順不順。
5. **打 API 的測試必須與 `frontend/src/api.ts` 的參數一致**
   （`objective: BALANCED`、`route_provider_preference: SIMULATED`、`traffic_mode: SIMULATED`）。
   API 自己的預設值是 `FASTEST`／`AUTO`／`AUTO`，會建立一個 demo 永遠不會用到的排班。
   `scripts/run_intent_routing_evals.py` 已修正，照抄它就對了。
6. **「跑一次對」不算通過，要「每次都對」。**
   每個測項在每組資料至少跑 2 次，兩次工具必須相同。
   已實測 W5、W7 會在兩次完整走查之間跑到不同工具——**不穩定的路由比壞掉更危險**，
   因為它會在彩排時通過、在台上失敗。

### BUG-10 — 跑過一次「已發車」之後，狀態永遠清不掉（2026-09-12 20:40 實測，**最高優先，demo 殺手**）


**畫面與後端互相矛盾**，而且使用者完全看不出來。

**復現步驟**（每一步都實測過）：

1. 匯入 `demo-50-tight.xlsx` → 開始裝車 → 模擬出發 → 拖時間軸（產生已送達的站）
2. 重整瀏覽器（F5）
3. 重新匯入同一份檔案 → 新的 `plan_id`
4. 打「三號車今天不能出車」

- 重整瀏覽器 → 同一個 session，狀態留著
- 「重新開始」→ 只清前端畫面，沒有換 session
- 新的 dataset／plan → 不影響 session 上掛的 stage 與 frozen stops

1. `session_id` 改為每次載入頁面時產生（例如 `CONVERSATION-${uuid}`）。
2. 「重新開始」必須同時換一個新的 `session_id`。
3. 後端應在 dataset 更換時清除該 session 的 stage 與 frozen stops，
   不能只靠前端自律。

VEH-001（81%）與 VEH-002（100%）既非最重也非最空，問它們就會答錯。

**為什麼這條最嚴重**：
QA playbook **A-2 就是「這個 AI 會不會算錯？」**，腳本寫的是
「打 `哪台車載重最高` → 系統回一個數字 → **當場對照畫面上車輛概況的數字**」。
評審只要改問「那一號車呢」，畫面上的數字和對話裡的數字就對不起來。

這也直接打臉整個架構主張（「LLM 不做算術，數字全部來自確定性工具」）——
數字確實來自工具，但**回答的是另一個問題**。

**修法**：新增 `vehicle_load`（查指定車輛）工具，參數為 `vehicle_id`，
回傳該車的計畫載重、上限、使用率、剩餘容量。
並在三個工具的描述中寫清楚邊界：

- `highest_load_vehicle`：只在問「哪一台**最重**」時使用
- `lowest_load_vehicle`：只在問「哪一台**最空／最少**」時使用
- `vehicle_load`：使用者**點名某一台車**時一律用這個

**判定失敗**：對四台車分別問「N 號車載重多少」，
任一台回覆中的 `vehicle_id` 與使用者點名的車不符，或數字與畫面不一致。
四台都要測，不得只測極端值。

## 回報格式

每一區塊跑完後，在 `docs/progress.md` 用這個格式記錄：

```
- 情境 Eval [區塊] — 通過 X/Y
  失敗項目：A-03（連續兩輪相同缺漏訊息）、B-02（兩張卡同車同站）
  每個失敗項附：實際輸入、實際輸出逐字、截圖檔名
```

**失敗項必須貼出系統的實際回覆逐字**，不得只寫「失敗」。
**不得修改「輸入」欄位的句子來讓測試通過。**
