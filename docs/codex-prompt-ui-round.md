## ⛔ 驗證方式只有一種，沒有例外

**全部都要開瀏覽器、在畫面上用鍵盤把字打進輸入框、按送出、看畫面上回什麼。**

- **禁止**用 `requests`、`curl`、Playwright 的 `page.request`、或任何直接打 API 的方式當作通過的證據。
- **禁止**只看 `evidence` 裡的 `tool` 名稱就說通過。**要看畫面上實際顯示給人的那句話。**
- Playwright 一律用 `pressSequentially()` 一個字一個字打進
  `getByRole('textbox', { name: '輸入訊息' })`，再 `press('Enter')`。
- 每一句都要截圖，存 `docs/screenshots/`，檔名對應測項編號。
- 回報時附截圖檔名與**畫面上實際出現的文字**，不是 API 的 JSON。

**理由**：先前有三輪用 API 測「通過」，但使用者在畫面上打同一句話得到的是罐頭訊息或原始 JSON。
API 通過不等於畫面通過，只有畫面上的字算數。

- 每個欄位標題可點排序，再點反向，標題上要有**箭頭**；
  鍵盤要能操作（`<th>` 裡放 `<button>`，有 focus 樣式）

## D-6 拖拉換站序，而且要即時算

- 拖曳一列到新位置，**還沒放開就要顯示**：能不能接受、該車里程增減、
  受影響站點的 ETA 變化、載重率變化
- 放開後**仍不得直接生效**，要人按確認才套用、版本 +1
- 不能換時要說原因：超出配送時段、超載、跨出可服務行政區、已發車的站不能動
- `DISPATCHED` 階段已完成的站不能拖
- 跨車輛拖曳：做得到就做，做不到就明確擋下並說明，不要默默失敗

**數字一律由後端確定性程式算，不准在瀏覽器裡自己算一套，也不准讓模型判斷。**
畫面自己算會跟求解器分岔，這個專案的賣點就是每個數字查得到出處。

作法：新增輕量端點，輸入「某台車的新站序」，輸出可行性與各站 ETA／里程／載重。
**不要重跑 OR-Tools**——站序是給定的，照順序把距離矩陣與時窗重算一遍即可；
`src/services/dispatch_parameters.py` 的 `_parameterized_route()` 已是這個模式，照抄改寫。
前端在拖曳目標改變時 debounce 150–250 ms 呼叫，**回應要在 200 ms 內回來**。

### 驗收
拖曳過程中就看得到可行性與變化數字；合法交換確認後版本 +1；
違反時段的交換明確拒絕並說原因；已發車後拖已完成的站不允許；
端點回應時間實測貼出來；截圖三張存 `docs/screenshots/`。
