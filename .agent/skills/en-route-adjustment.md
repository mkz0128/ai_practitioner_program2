# 發車後調整與偏差記錄（F5／F6）

## 觸發

- 車輛已發車（`DISPATCHED`），既有訂單須提前抵達。
- 客戶來電要求改時段。
- 查詢今日配送偏差或參數建議。

## 不觸發

- 車輛尚未發車 → `daily-dispatch` 或 `urgent-insertion`。
- **F5 不是插入新訂單**，是調整既有訂單的順序或時段。

# F5 — 發車後路線調整

## 求解範圍

| 項目 | 狀態 |
|---|---|
| 車輛指派 | **凍結** |
| 已完成站點 | **凍結** |
| 路徑起點 | 車輛當前位置（非 depot） |
| 剩餘站點順序 | 可調整 |
| 路徑終點 | `DEPOT-001` |

`completed_stops` 與 `current_position` 由時間軸滑桿推進、依 ETA 推導。**不引入 GPS 或 WebSocket。**

## 兩種真實動作

| 客戶說 | 做什麼 | 系統回 |
|---|---|---|
| 「能不能早點？」 | 提高該車剩餘站點中的順序 | 「提到第 3 站，**預估** 11:20 到」 |
| 「改成上午好了」 | 切換時段 | 「這台車上午已滿，改派 VEH-004 可行」 |

**系統輸出的是預估抵達時間，不是承諾。** 宅配業只承諾時段、不承諾時點。決定是否答覆客戶的是調度員。

## 額外要求

發車後改動代價極高（司機需接電話、重看導航、可能已駛過），因此每張方案卡**必須輸出「為什麼值得繞這一趟」的理由**，不能只給數字。

範例：
> 「這樣改，司機要多繞 4.1 公里。但 ORD-019 準時，而且沒有人因此掉出時段。」

## Guardrails

- 不得改變任何車輛指派。
- 不得改動已完成站點。
- 不得插入新訂單，除非順路且完全可行。
- 方案卡仍須通過獨立 Validator。
- 人工確認前不改變 current version。

# F6 — 偏差記錄與參數修正

## 資料來源

**不建立司機回報資料模型。** 滑桿推進時的進度即為「實際」，與系統預估比對產生偏差：

```
系統預估：VEH-003 第 5 站 10:20 抵達
滑桿推到 10:20 → 實際仍在第 4 站
                 ↓
        偏差 = 慢 22 分鐘，自動記錄
```

## 兩類偏差

| 類型 | 產出 |
|---|---|
| **車輛偏差** | 「VEH-003 今天比預估慢 22 分鐘。已記錄。下次排班會調高這台車的行駛時間估計，或少排 2 站。」 |
| **區域偏差** | 「Z5 區每站停留比預估多 4 分鐘。已記錄。建議將 Z5 服務時間由 3 分鐘調為 7 分鐘。」 |

## Guardrails

- 只記錄與**建議**，絕不自動套用參數；調整須人工確認。
- 偏差統計由確定性程式計算，**LLM 不產生任何數字**。
- 回顧範圍為單日。
- 不引入 GPS、司機 App 或電子簽收。
