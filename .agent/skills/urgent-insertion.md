# 臨時插單（F3 上車前／F4 上車後）

## 觸發

方案建立後、車輛發車前，使用者提出一張或多張臨時訂單。

## 不觸發

- 車輛已發車 → `en-route-adjustment`。
- 既有訂單要提前 → `en-route-adjustment`。

## 階段差異（唯一的分歧點）

| | F3 上車前（`PROPOSED`） | F4 上車後（`LOADED`） |
|---|---|---|
| 進入條件 | 預設 | 調度員手動按「開始裝車」 |
| 跨車移動既有訂單 | 允許 | **拒絕** |
| 完整重排 | 允許 | 拒絕 |
| 調整順序 | 允許 | 允許 |
| 新單可進的車 | 任一合法車輛 | 仍有餘裕的車輛 |

**F4 禁止跨車的理由是物理性的**：裝車依配送順序反序堆放，一旦開始裝車，順序已固化在車廂裡；跨車移動代表要卸貨重裝。拒絕時必須說明此理由，不得只回錯誤碼。

## 執行步驟

1. Agents SDK 只把自然語言整理成 strict structured output，**不直接執行求解**。
2. 程式狀態機逐張檢查必要欄位。有缺漏時一次列出全部，不開始計算。
3. 僅有訂單 ID 時先查既有資料；查不到就要求補齊。
4. 欄位完整後顯示全部摘要，等待使用者選擇「產生方案」。
5. **多張訂單一律整批求解**，共用同一 base version 與同一份矩陣。
6. 產生 2–4 張方案卡（見下）。
7. 執行獨立 Validator。
8. 人工以精確 `plan_id`／`version` 確認後才建立新版本。

## 方案卡規則

**整批是一起「算」，不是一起「送」**——每張單仍各自去最適合的車。卡片內容須逐張列出安排位置。

1. **每張卡都必須完全可行**：全部訂單在時段內、無超重、無跨區、不違反 `DispatchRule`。不可行的結果只能作為「排不進去」的說明，不得偽裝成選項。
2. **每張卡必須標示代價**：增加的距離與時間、換車數、載重餘裕。
3. **只列需要人工決定的**；影響輕微者摺疊為一行摘要。
4. 批次中有訂單無法安排時，方案卡仍須成立並標示需人工處理，**不得整批失敗**。

## 對話修改（白名單，其餘一律拒絕）

| 可說的話 | F3 | F4 |
|---|---|---|
| 「這單改派給四號車」 | ✅ | ❌ |
| 「這單改成上午送」 | ✅ | ✅ |
| 「這單改明天送」 | ✅ | ✅ |
| 「先送這單」 | ✅ | ✅ |
| 「三號車不要動」 | ✅ | ✅ |
| 「不要讓任何人遲到」 | ✅ | ✅ |

每次修改重新求解並產生**新的一組卡**，不就地編輯舊卡。白名單以外不得由 LLM 自行詮釋。

## Guardrails

- 方案卡絕不覆寫 base plan；版本不符必須拒絕。
- LLM 不得直接呼叫求解、不得用 regex 或關鍵字決定意圖、不得跳過摘要確認。
- 任何一張缺欄時，整批不得開始計算。
- 重複 ID、無法安排或 Validator 失敗不得污染 current plan。
- 不得捏造訂單或缺漏值。

## 失敗處理

| 情況 | 回應 |
|---|---|
| 訂單無效 | `URGENT_ORDER_INVALID` |
| 無可行插入 | 出「排不進去」卡片，保留原方案 |
| 版本過期 | `PLAN_VERSION_CONFLICT` |
| 階段不允許的操作 | 明確拒絕並說明物理／規則理由 |
